## Event, Bedingung, Aktion

**Tafelbild:** Die Tür als Kette in drei Spalten. Event: Zone, Betreten. Bedingung: Wenn, Schlüssel da?, gespeist von der Variable Ja-Nein „Schlüssel vorhanden“. Aktion: bei Ja Bewegen, die Tür fährt hoch; bei Nein Text setzen, „Verschlossen.“

[Event](https://www.allknivesnobagel.com/teaching/gec1/concepts/event/): ein Moment

[Zustand](https://www.allknivesnobagel.com/teaching/gec1/concepts/state/): was das Spiel sich merkt

[Bedingung](https://www.allknivesnobagel.com/teaching/gec1/concepts/condition/): ja oder nein

Ein [Event](https://www.allknivesnobagel.com/teaching/gec1/concepts/event/) ist ein Zeitpunkt, an dem etwas passiert: Betreten, Drücken, Aufprall. In Besteck lösen solche Momente die **Auslöser** aus. Ein [Zustand](https://www.allknivesnobagel.com/teaching/gec1/concepts/state/) bleibt von Frame zu Frame erhalten, etwa ob der Schlüssel schon aufgehoben ist; in Besteck steht er in einer **Variable** (eine Zahl, ein Ja-Nein oder ein Text mit Namen). Eine [Bedingung](https://www.allknivesnobagel.com/teaching/gec1/concepts/condition/) fragt diesen Zustand in dem Moment ab, in dem das Event ankommt, und schickt es auf den einen oder den anderen Weg.

## Wo wohnt die Logik?

**Tafelbild:** Links der Inspector der Tür: Transform, Mesh Renderer, Box Collider, darunter die Logik mit dem Logik-Graph „Tür öffnen“. Rechts der Graph: Zone, Betreten, führt zu Bewegen; dessen ◆ Objekt ist Dieses Objekt. Ein Kreidebogen von Bewegen zurück zum Transform der Tür: steuert.

Tür auswählen, Add Component › Besteck › Logik.

Logik ist selbst eine [Komponente](https://www.allknivesnobagel.com/teaching/gec1/concepts/component/), die andere Komponenten steuert.

Die **Logik** ist eine Komponente wie Rigidbody oder Box Collider: auswählen, im Inspector **Add Component**, „Logik“ tippen. Sie spielt einen **Logik-Graph** ab, eine Datei im Projekt, so wie ein Animator seinen Animator Controller abspielt. Die Knoten im Graph steuern andere Komponenten: **Bewegen** den Transform, **An/Aus** das ganze GameObject, **Kraft** den Rigidbody. Das Objekt, auf dem die Logik sitzt, heißt im Graph **Dieses Objekt**; in einem C#-Skript wäre das `gameObject`. Ein neuer Graph bringt den Knoten **Dieses Objekt** schon mit; ein Draht von seinem ◆ zu Bewegen sagt: Bewege mich.

## Komponente oder Graph?

**Tafelbild:** Links: Was einem Objekt gehört, ist eine Komponente. Die Wache trägt Verhalten, Variable „Geduld“ und Rigidbody. Rechts: Was mehrere verbindet, ist ein Graph. Schlüssel, Türzone und Tür sind über Referenzen mit dem Logik-Graph „Tür öffnen“ verbunden.

Gehört es einem Objekt: Komponente.

Verbindet es mehrere: Graph.

Besteck bringt beides. Was nur ein Objekt betrifft, ist eine Komponente an diesem Objekt: **Add Component › Besteck › Variable** für einen Wert, der zu ihm gehört, **› Verhalten** für eine Figur, die patrouilliert oder folgt, **› Kamera** für einen festen Blick. Was mehrere Objekte zusammenbringt, steht in einem Logik-Graph; die anderen Objekte spielen darin **Rollen**. Die Logik ist die Brücke dazwischen: Sie selbst ist eine Komponente der Tür, und der Graph, den sie abspielt, verbindet die Tür mit Schlüssel und Zone. Das ist eine Faustregel, kein Gesetz. Unity selbst ist so gebaut, und dieselbe Frage stellt sich später bei jedem eigenen C#-Skript: Wem gehört dieses Verhalten?

## Drei Arten von Drähten

**Tafelbild:** Drei Drahtarten. Event, gestrichelt: wann etwas passiert, etwa Betreten zu Prüfen. Daten, durchgezogen: ein Wert, der gelesen wird, etwa Wert zu Bedingung. Referenz, doppelt: welches Objekt gemeint ist, etwa Schlüssel zu An/Aus.

Der [Graph](https://www.allknivesnobagel.com/teaching/gec1/concepts/graph/) kennt drei Drahtarten. ▶ Events laufen von links nach rechts durch die Kette. ● Daten werden gelesen, wenn ein Knoten sie braucht. ◆ Referenzen sagen einem Knoten, mit welchem Objekt in der Szene er arbeitet: mit **Dieses Objekt** oder mit einer **Rolle**. Hängen an einem Event-Ausgang mehrere Drähte, tragen sie Nummern: Nr. 1 läuft zuerst. Falsche Verbindungen lassen sich gar nicht ziehen: Ein Event-Ausgang passt nur auf einen Event-Eingang.

**Screenshot:** Das Graph-Fenster „Tür öffnen“ mit vier Knoten: links Rolle: Schlüssel, Rolle: Türzone und Rolle: Schild, jede mit einem gelben Warndreieck, weiter rechts Dieses Objekt (Tür). Noch keine Drähte. (Unity 6.3 · Besteck 0.5).

Ein Draht von dort sagt einem anderen Knoten, mit welchem Objekt er arbeitet.

Darum können zwei Türen denselben Graph abspielen: Für jede ist **Dieses Objekt** sie selbst, und jede hat ihre eigenen Variablen.

|---|---|---|

Dann Play: Schlüssel ansehen, **E** drücken, zur Tür gehen. Gespeichert wird von selbst: Vor jedem Play speichert Besteck offene Graphen und prüft alle Logiken; was fehlt, steht als Warnung in der Console.

**Wenn es hängt:**

- Ein Objekt lässt sich nicht hineinziehen oder bleibt ungebunden: Das Graph-Fenster weiß nicht, welche Logik gemeint ist (etwa nach einem Doppelklick auf die Datei). Den Graph über **Graph öffnen** an der Logik der Tür öffnen, oder unten links im Graph-Fenster die Logik wählen.
- Bewegen meldet „◆ Objekt fehlt“: Der Draht von Dieses Objekt zu Bewegen fehlt.
- Wenn sagt immer Nein: Der Draht von Ja-Nein · Wert zu Wenn · Bedingung fehlt.
- Zone zeigt nie ✓: Is Trigger fehlt, die Zone liegt nicht im Weg, oder sie ist zu klein (grüner Rahmen in der Scene-Ansicht).
- Der Schlüssel reagiert nicht auf E: näher als 3 m herangehen und ihn ansehen; er braucht seinen Box Collider.

## Woran merkt man, dass der Schlüssel benutzbar ist?

Benutzen meldet auch **Im Blick** und **Nicht mehr im Blick**.

Was dann passiert, entscheidet ihr.

Zum Beispiel ein Schild, ein Leuchten oder ein leiser Ton.

„Im Blick“ feuert, sobald der Blick das Objekt in Reichweite trifft, „Nicht mehr im Blick“, sobald er es wieder verlässt. Was der Spieler dann sieht oder hört, baut ihr selbst, mit Knoten, die ihr schon kennt: Im Blick → **Text setzen** „E: aufheben“ und Nicht mehr im Blick → **Text setzen** mit leerem Text; oder ein kleines Licht über dem Schlüssel mit **An/Aus**; oder **Ton abspielen**. Das ist [Feedback](https://www.allknivesnobagel.com/teaching/gec1/concepts/feedback/): wie das Spiel dem Spieler sagt, was möglich ist. Ein leuchtender Umriss passt zu einem Abenteuer, ein Flüstern zu einem Horrorspiel, gar nichts zu einem Spiel über das Suchen.

Wer den Satz nicht sagen kann, hat noch keine klare Interaktion. Das gilt auch für die eigene Spec.

## Collider oder Trigger?

**Tafelbild:** Links eine feste Wand: Die Kugel prallt ab, Unity meldet OnCollisionEnter. Rechts eine gestrichelte Zone: Die Kugel rollt hindurch, Unity meldet OnTriggerEnter.

[Kollision](https://www.allknivesnobagel.com/teaching/gec1/concepts/collision/): fest oder durchlässig.

Is Trigger ist ein Haken am Collider.

Ein Collider ist die unsichtbare Form, mit der ein Objekt an der [Kollision](https://www.allknivesnobagel.com/teaching/gec1/concepts/collision/) teilnimmt. Ein normaler Collider ist fest. Mit **Is Trigger** wird er durchlässig und meldet nur noch, dass etwas hinein- oder hinauskommt. Die beiden Meldungen haben verschiedene Voraussetzungen:

| Meldung | Auslöser in Besteck | wann sie kommt |
|---|---|---|
| Trigger: `OnTriggerEnter` | **Zone** | eines der beiden Objekte hat einen [Rigidbody](https://www.allknivesnobagel.com/teaching/gec1/concepts/rigidbody/) (auch kinematisch) oder einen CharacterController, wie die Spielfigur |
| Aufprall: `OnCollisionEnter` | **Zusammenstoß** | mindestens eines der beiden hat einen Rigidbody, bei dem Is Kinematic aus ist |

Darum meldet die Spielfigur Zonen zuverlässig, aber keinen Aufprall: Läuft sie gegen eine Wand, gibt es kein `OnCollisionEnter` und der Auslöser Zusammenstoß bleibt still. Der CharacterController hat dafür eine eigene Meldung, `OnControllerColliderHit`, die Besteck nicht als Knoten anbietet. Zusammenstoß gehört an Dinge mit Rigidbody: eine Kiste, die auf den Boden fällt, ein Ball, der gegen eine Wand rollt. Diese Meldungen empfängt die Komponente **Rolle** am jeweiligen Objekt; im Play-Modus zeigt sie, was angekommen ist.

## Ein Rigidbody übergibt an die Physik

Mit [Rigidbody](https://www.allknivesnobagel.com/teaching/gec1/concepts/rigidbody/) fällt der Würfel.

1. Kiste in die Luft, Add Component › Rigidbody, Play
2. Die Falle: Logik auf die Kiste, Zone → Kraft
3. Kraft: Richtung 0, 1, 0, Stärke 6, Stoß

Felder: Mass, Use Gravity, Is Kinematic

Mit Rigidbody bestimmt die Physik die Position. Wer die Transform trotzdem direkt verschiebt, arbeitet gegen sie; das Objekt ruckelt oder rutscht durch Wände. **Is Kinematic** heißt: Die Physik bewegt das Objekt nicht, ein Skript oder eine Animation tut es. Auf einen kinematischen Körper wirkt auch der Knoten Kraft nicht; er meldet das. **Constraints** sperren einzelne Achsen, etwa damit eine Figur nicht umkippt.

Modelle aus einem Asset-Pack bringen meist keinen Collider mit: ohne ihn fallen sie durch den Boden, und Zone, Benutzen und Zusammenstoß bemerken sie nicht. Also **Add Component › Box Collider**. Die Größe stimmt auch nicht immer: Eine Kiste aus einem Pack ist oft nur 0,5 m hoch. So eine kleine Kiste kippt leicht, und Stufen bis 0,35 m nimmt die Spielfigur von selbst. Zum Schieben die Kiste lieber auf etwa 1 m skalieren.

Ein Aufprall lässt sich jetzt auch hören: Die Kiste bekommt eine eigene Logik (Add Component › Besteck › Logik, **Neu**), darin **Zusammenstoß** mit ◆ Körper = **Dieses Objekt** · Getroffen → **Notiz in Konsole**. Fällt die Kiste auf den Boden, steht die Notiz in der Console. Das geht, weil die Kiste einen Rigidbody hat; an der Spielfigur bliebe Zusammenstoß still.

Die Falle, im Kurs vorgeführt und nach diesem Rezept nachzubauen, gehört in dieselbe Logik, denn es ist die Kiste, die springt: **Zone** (◆ Zone: eine Trigger-Box vor der Kiste, aus der Hierarchy hineingezogen) · Betreten → **Kraft** · Anstoßen, ◆ Körper = **Dieses Objekt**. **Stoß** wirkt einmal, wenn das Event ankommt. **Dauerkraft** schiebt so lange, bis der Eingang **Stopp** kommt, etwa von Zone · Verlassen.

Wie so etwas in einem fertigen Spiel aussieht: In HIGH WATER (gebaut in Godot) ist jede Figur ein Rigidbody mit 3 kg. Im Stehen sind ihre Drehachsen gesperrt, damit sie aufrecht läuft; ein kräftiger Stoß hebt die Sperre auf, und die Figur kippt, rollt und wirft beim Aufprall andere um. In Unity hieße das **Constraints › Freeze Rotation**, im Code wieder freigegeben mit `rb.constraints = RigidbodyConstraints.None`.

## Kraft und Drehmoment

**Tafelbild:** Links: Eine Kraft am Schwerpunkt schiebt eine Kiste in eine Richtung, AddForce. Rechts: Ein Drehmoment dreht einen Balken um seine Achse, von oben gesehen, AddTorque.

Kraft: Knoten in Besteck

[Drehmoment](https://www.allknivesnobagel.com/teaching/gec1/concepts/torque/): fehlt in Besteck

Eine Kraft ist ein [Vektor](https://www.allknivesnobagel.com/teaching/gec1/concepts/vector/): Richtung und Stärke. `AddForce` schiebt den ganzen Körper, `AddTorque` dreht ihn um eine Achse. Beide gibt es als Stoß (`ForceMode.Impulse`, ein einzelner Moment, etwa ein Tritt) oder als gleichmäßiges Schieben (`ForceMode.Force`, in jedem Physik-Schritt, also in `FixedUpdate()`). Masse zählt: Die gleiche Kraft bewegt eine schwere Kiste weniger.

4. Collapse fasst gleiche Meldungen zusammen.

[Console](https://www.allknivesnobagel.com/teaching/gec1/concepts/console/): Window › General › Console

Strg + Umschalt + C

Die [Console](https://www.allknivesnobagel.com/teaching/gec1/concepts/console/) sammelt, was Unity und eure Skripte melden. Ein roter Kompilierfehler (`error CS…`) blockiert Play ganz, bis er behoben ist; Unity sagt dann „All compiler errors have to be fixed before you can enter playmode!“. Ein Laufzeitfehler (Exception) bricht nur das Skript an dieser Stelle ab, das Spiel läuft weiter. Steht dieselbe Meldung hundertmal da, kommt sie aus `Update()` oder `FixedUpdate()`: in jedem Frame einmal. **Clear** leert die Liste (Kompilierfehler bleiben stehen), **Error Pause** hält das Spiel an, sobald ein Skript einen Fehler meldet. ## Was ein Knoten braucht

**Tafelbild:** Links fünf Markierungen aus dem C#-Code, rechts der Knoten, der daraus entsteht. NodeInfo gibt Titel und Gruppe, Input den Eingang Drehen, Ref den Anschluss ◆ Körper, Setting die Einstellung Stärke, Output den Ausgang Angewendet.

Zwei Dateien in Assets › Eigene Knoten. Das Menü legt sie an.

Ein eigener Knoten besteht aus zwei Dateien, beide unter `Assets/Eigene Knoten`: `Drehmoment.cs` (der Knoten) und `Editor/DrehmomentNode.cs` (sein Gesicht im Graph-Editor). Das Menü **Tools › Besteck › Eigener Knoten (C#)** legt beide an, dazu die Assembly-Dateien des Ordners; dasselbe gibt es unter **Assets › Create › Besteck › Eigener Knoten (C#)**. Danach steht der Knoten unter „+ Knoten“ › Aktion › Drehmoment. Ohne `NodeInfo` landet er in der Gruppe „Eigene“ unter seinem Klassennamen. Im C#-Code heißt Besteck weiterhin `Kit`: `using Kit;`, `KitNode`.

So sollte der Diff aussehen

`Assets/Eigene Knoten/Drehmoment.cs`:

```csharp
// Drehmoment: ein eigener Besteck-Knoten, der einen Rigidbody um eine Achse dreht.
// Herkunft: geschrieben von einem Agenten (Werkzeug und Modell siehe KI-Verzeichnis),
// geprüft und getestet von <Name>, 20.11.2026.
using System;
using UnityEngine;
using Kit;

[Serializable]
[NodeInfo("Drehmoment", "Aktion", "Rigidbody um eine Achse drehen")]
public class Drehmoment : KitNode
{
    [Ref("Körper")] public Rigidbody body;
    [Setting("Achse")] public Vector3 axis = Vector3.up;
    [Setting("Stärke")] public float strength = 5f;

    [Output("Angewendet")] [NonSerialized] public Output applied;

    [Input("Drehen")]
    public void Spin(Signal s)
    {
        if (body.isKinematic) { Fail($"„{body.name}“ ist kinematisch: Drehmoment wirkt nicht"); return; }
        body.AddTorque(axis.normalized * strength, ForceMode.Impulse);
        applied.Fire(s);
    }
}
```

`Assets/Eigene Knoten/Editor/DrehmomentNode.cs`:

```csharp
// DrehmomentNode: zeigt den Knoten Drehmoment im Graph-Editor von Besteck.
// Herkunft: wie Drehmoment.cs.
using System;
using Kit.Editor;

[Serializable]
public class DrehmomentNode : KitEditorNode
{
    public override Type RuntimeType => typeof(Drehmoment);
}
```

## Kaputt? Zurück zum letzten guten Stand

**Tafelbild:** Eine Zeitleiste mit Commits: Blockout begehbar, Tür geht auf, Agent: Drehmoment. Der dritte ist kaputt. Ein neuer Commit Revert nimmt ihn zurück; der Fehler bleibt im Verlauf sichtbar.

Noch nicht committet: Discard changes

Committet: Revert Changes in Commit, ein [Revert](https://www.allknivesnobagel.com/teaching/gec1/concepts/revert/)

In GitHub Desktop: Reiter **History**, Rechtsklick auf den Commit, **Revert Changes in Commit**, dann **Push origin**. Ein [Revert](https://www.allknivesnobagel.com/teaching/gec1/concepts/revert/) löscht nichts. Git legt einen neuen Commit an, der die Änderungen eines alten zurücknimmt; beide bleiben im Verlauf. Das ist sicher, auch wenn der kaputte Stand schon gepusht ist. Noch nicht committete Änderungen verwirft in GitHub Desktop **Discard changes** (Rechtsklick auf die Datei). Vor dem Revert in Unity alles speichern; danach lädt Unity die geänderten Dateien neu. Im Terminal: `git revert <Kennung>`.
